# SHERPA Render Policy

**One line:** Decides per turn how many sketches to show (N) and along which variation axis — producing COMMIT (1), FORK (2), SWATCH (3), or SWIPER (7) mode.

**Destination picker (2026-06-22):** `RenderMode.DESTINATION_PICKER` is an additional, product-free mode emitted by the light destination finder (not the render-policy decision tree). The `SketchFrame` carries the cards in a new optional `destinations: list[dict]` field — `{name, country, iata, tags[], match (int), climate_note (str)}` — with `sketches=[]`, `variation_axis="destination"`. Gated in `cognitive/handler.py` by `if discover_only or not city` (resolves before the committed-city fast-path short-circuit). Streams inside the existing `block.type == "sketch_frame"` envelope (no AppSync schema change).

**Destination Finder v2 — feasibility gate + climate rank + richer card (2026-06-23):** `_discover_destinations_light` (`cognitive/sketch_engine.py`) now turns the picker from a pure taste-match into a feasibility-aware recommender. **DNA SQL is unchanged** — origin point, budget ceiling, pax, and desired climate are per-user/per-turn values, not catalogue columns, so the DNA `destinations` endpoint stays origin/budget-agnostic. Instead **SHERPA over-fetches** a wider pool (`limit = max(top_n*3, _DEST_POOL_N=12)`) from dna-shortlist and **gates + relaxes + climate-re-ranks + slices** in the finder. Build order is load-bearing: **gate (exclude unaffordable) → relax-backfill stretches → climate soft re-rank → slice to top_n → THEN compute match% over the shown set** (recomputing after the slice preserves the score stretch despite the over-fetch). The dna-shortlist `destination_codon_search(k=limit)` comment notes this (no DNA code change; SHERPA owns the stretch via post-slice recompute).

Feasibility model (all per-turn, finder-local): distance (`_haversine_km_flight` over IATA→coords from the **ti-airports DDB cache index**, never OpenFlights airports_map) → flight hours (`dist/_CRUISE_KMH + _OVERHEAD_H`) → round-trip economy fare (`cabin_fare_estimator.estimate_fares` is **one-way USD** → ×2 round-trip → **USD→EUR via `_USD_PER_EUR`≈1.08** → ×`max(adults+children,1)`). Compared like-for-like against an **all-pax EUR** ceiling (`flight_ceiling_abs`, else `budget_abs*_FLIGHT_BUDGET_FRACTION=0.40`, else None): `≤ceiling`→`within`, `≤ceiling*_STRETCH_MAX(1.4)`→`stretch`, else `unaffordable` (excluded). Climate intent parsed locally (`_parse_climate_intent` keyword→°C band, or warm/beach DNA default) — additive `±_CLIMATE_BONUS/_PENALTY` on top of DNA coverage (DNA dominates). Graceful degrade: no origin resolvable → flight gate skipped (taste+weather only); null lat/lon → card kept, no estimate, affordability null (never excluded on missing data); no budget → keep all (+ optional soft long-haul demote for thrifty BUDG DNA). **Climate JSONB is keyed by 3-letter month abbreviation (`_MONTH_ABBR` "jan".."dec"), not full names** — `climate_note` from `month["notes"]`, weather avg from `month["avg_temp_c"]`.

**Destination REASON layer + the badge rule (ticket 16, 2026-08-10):** the design rule ("What a destination card may claim") is that **a match score may never appear alone — if no reason can be derived from something the traveller said OR SAVED, the badge does not render.** `_build_destination_why` (`cognitive/sketch_engine.py`) composes that reason deterministically (never an LLM) and returns `(why, match_signals, why_inputs)`, the SAME shape as the flight layer (`flight_ranker._build_flight_why` → `FlightOfferBlock.why` / `.match_signals`). **Three new destination-card fields (additive, optional):** `why` (str — the first one or two signals joined " · ", for the card face), `match_signals` (list[str], capped at `_REASON_MAX_SIGNALS=3`), `why_inputs` (list of `{source, said, score, used, codon_id}` — EVERY considered input including the ones that failed their gate, so a suppressed badge is explainable in the DDB trip log). **`codon_id` (added 2026-09-02, additive):** the DNA codon behind the input, so the client can colour a "Why it's yours" row by its chromosome (the prefix before `#`) exactly as the DNA page does. Present on every entry; **non-null only for the two codon-backed sources** (`codon`, `taste`) and `None` for the scored priors (`mood`/`climate`/`visa`/`business`), which are attributes, not codons. The per-row WEIGHT rides on the existing `score`: a real DNA affinity for `taste`, and **`None` for a stated `codon` — set membership has no magnitude and destination-side `vibe_weights` is NULL on all 1094 rows, so a number there would be invented**. `SketchFrame.destinations` stays free-form `list[dict]`, so **no forwarder-allowlist change is needed** (that allowlist governs `/turns` + `/trip/init` REQUEST fields only).

**Reason sources — four, in the order they are voiced.** ① the EXPLICIT mood prior, cited **per mood and gated on THAT mood's own row score** (`e["mood_row_scores"]`, 0-100 column ÷ 100), never on `prior_scores["mood"]` — that entry is the AND-semantics MEAN that moved the rank and cannot license an individual claim (romance 100 + wellness 60 → mean 0.80 clears the bar while the wellness claim itself is unchecked); an unscored mood is ABSENT from the map, never 0.0. ② stated session codons the destination's `vibe_codons` actually carry (the same predicate that admitted the row to the coverage pool). ③ the other EXPLICIT soft priors (climate / visa / business), each clearing `_REASON_MIN_SCORE` (env `FINDER_REASON_MIN_SCORE`, 0.8) on its own `finder_score`, paired where possible with a fact already printed on the same card (the weather strip, the visa row). ④ **SAVED TASTE** — a codon the traveller's DNA holds at ≥ `_TASTE_MIN_AFFINITY` (env `FINDER_TASTE_MIN_AFFINITY`, 1.0; ±0.015 card-feedback strokes never qualify) that this destination also carries, top `_TASTE_MAX_CODONS=3` by affinity. This is the design's "or saved" half and it is what lets a **taste-ranked deck keep its badges**. **Excluded on purpose:** a DNA-LEAN prior (`explicit=False`/NUDGE_W — an inference we drew, e.g. "beachy DNA ⇒ they want warm") and the raw DNA cosine. Vocabulary lives in ONE table, `_CODON_MEANING` (codon → `(said, saved)`); the `said` column doubles as the dedup key so a codon both stated and saved is voiced once (stated wins). Hotel-shaped codons (`STAY.*`, `BUDG#*`) are deliberately absent — a city has no room tier.

**Destination `reason_evidence` — the discriminating half of the sentence (SC-43, 2026-09-02):** the reason layer above says what the TRAVELLER brought to a card. `reason_evidence` says what is true of **THIS city and no other in the deck**, and it REPLACES the catalogue `blurb` the card used to append. Why it was needed: measured live, Paris and Florence return **identical `match_signals`**, so no client-side change could ever separate them — the discrimination has to be server-side or it cannot exist.

**Source.** `destinations.vibe_evidence` (Aurora JSONB, `{codon_id: quote}`), one sentence lifted from the source article that justified each codon, from the local re-enrichment: **902 of 1094 rows, ~50 codons each, 45,228 quotes**, mirrored to DDB `mywai-prod-ti-city-enrichment` as a native Map of Strings (906 items — 4 cities exist under two `countryCode` partitions). The ETL writer emits a targeted SET over an enumerated attribute list that never names `vibe_evidence`, so an enrichment run does not clobber it. The destinations-sync upsert enumerates its columns and does not carry it either, so an Aurora resync does not wipe it.

**Transport.** `destination_codon_search` (`dna/lambda/shared/pg_client.py`) SELECTs the column and emits **`evidence`** on each row — `{codon: quote}` restricted to `query codons ∩ row.vibe_codons`, the SAME intersection `COVERAGE_EXPR` scores (no second query, no new bind param), capped at **8 codons × 300 chars** (env-overridable), weight-ordered. The raw ~50-key map is **popped** off every row so it cannot travel. A JSONB column arrives through the RDS Data API as a **string** — DNA parses it once and emits a dict; readers should code for the dict. **Additive only:** the three built SQL templates differ by exactly one projection line, and every destination ORDER BY already ends `…, d.population DESC NULLS LAST, d.geoname_id ASC` (the TEXT PK), so the sort is TOTAL and a widened projection can change the query plan but never which rows the LIMIT cuts.

**Composition.** `_attach_reason_evidence` (`cognitive/sketch_engine.py`) picks **deck-relatively**: a card takes the quote for the codon it carries that the rest of the deck does NOT, so the clause earns its place by being unrepeatable. **A clause already printed is refused, in both passes** — deck-level uniqueness is the invariant (exact-string; near-duplicate boilerplate is the accepted falsifier). Assignment is **greedy in rank order, not globally optimal**: where several cards share their only distinguishing quote the tail goes bare rather than repeating. Quality floor and a **110-char bound cut at a clause boundary**, because these are raw article sentences and some say nothing ("Many restaurants and cafés serve local food" is rejected). **Never an LLM** — composition over data already held, the same principle as the typed-mood ruling in SC-42.

**Absent is a first-class state,** not a failure: 192 of 1094 cities have no evidence. The field is then **omitted** (never empty-string, never a placeholder) and the card prints its attribution alone — shorter and still true. The client keeps composing from `match_signals` in that case, so that path is not a fallback to be deleted. Purely additive and tested as such: the same rows with and without `evidence` produce **byte-identical cards** once `reason_evidence` is stripped — ranking, `match`, `why`, `match_signals`, `why_inputs` all unmoved.

**Destination `taste_evidence` — the receipt behind the match badge (ticket 144, 2026-09-06):** ticket 141 put a real number on the card ("shares 23 of your 39 tastes") while the overlay under it could name **three**, because SHERPA's `why_inputs` is capped at `_TASTE_MAX_CODONS` = 3 and phrase-gated to the 39 codons `_CODON_MEANING` can voice. A percentage whose evidence stops at three rows is unfalsifiable, so `destination_codon_search` now emits **`taste_evidence`** on every row: `{families: [{chromosome, n_hit, n_total, covered, mass, hits: [{codon_id, w, s}]}], n_hit, n_total}`.

**Why DNA and not SHERPA.** The weighted query (`codons` / `weights` from `_coverage_query_arrays`) exists only in `pg_client`; re-deriving it a Lambda hop later would be a second definition of "the traveller's tastes", and two definitions drift. Same discipline as 141's numerator and denominator coming out of one SQL expression. Pure projection applied beside `_attach_destination_evidence` — no second query, no bind param, no LLM, no schema change, and it reads no evidence column, so the 192 quote-less cities carry a full receipt.

**What `covered` asserts.** Per chromosome F, `Σ_{c ∈ F ∩ row.vibe_codons} w·s ÷ Σ_{c ∈ F} w` — `COVERAGE_EXPR` restricted to one family. **Absolute, 0–1, no per-card normalisation**, so the same "5 of 8" draws the same arc on every card and two cities are comparable. The **mass-weighted mean of the families equals the row's raw coverage**, so the rings and the badge reconcile by construction (locked by `tests/test_dest_taste_evidence.py`). `s` mirrors the shipped coverage expression including its fallback: **1.0 under membership** (the default — exact, not an approximation), `vibe_weights` per codon with an ELSE of 1.0 under `DEST_WEIGHTED_SCORING`. ⚠️ `vibe_weights` is **not in the destination projection today** — irrelevant with the flag off, and logged (`taste_evidence_weights_missing`) rather than assumed away if it is turned on.

**Families with no hits are EMITTED**, with `n_hit` 0: that is the empty ring track, the visible reason the number is not 100. Grouping uses the **client's** chromosome keys (a mirror of `dnaParser.ts` `PREFIX_MAP` — `FAMI` and `SOC` are one `social` family; an unknown prefix falls to `other`, never a guess). Order is family mass DESC then key — stable for a traveller across the whole deck. **`stated` is NOT set here**: `destination_codon_search` receives the merged query and sees the session set only as the evidence-widening list, so the this-turn flag and the stated-first promotion belong one layer up, where SHERPA holds `_stated_codons`. `DEST_TASTE_EVIDENCE_MAX_HITS` (60) trims the **named** hits only — `n_hit` / `n_total` / `covered` are always computed over the full set. ≈1 KB/card on the same AppSync frame.

**SHERPA stamps what was said THIS TURN, and promotes it (`_stamp_taste_evidence`, `sketch_engine.py`).** `_to_card` copies the row's `taste_evidence` onto the destination card through this function, which returns a **new** object (the row is never mutated — `_attach_reason_evidence` reads it afterwards) or `None`, in which case the key is **omitted, never nulled**. The stated set is `session_intent_codons` — Sonnet-extracted from the traveller's own message and whitelisted by `intent._VALID_SESSION_CODONS`, NOT `query_implied_codons` and NOT the evidence-widen list. Two additions and two orderings: a hit whose codon was stated carries `stated: true` (**omitted when false** — absence is the negative, so a renderer cannot confuse "not asked for" with "we did not look"); a family holding one carries `stated: true`; a stated codon **leads** its family's run-in and its family **sorts to the top of the list**, with DNA's own order (family mass DESC / hit weight DESC) preserved inside each group. **Nothing is capped here.** `_TASTE_MAX_CODONS` = 3 bounds the card FACE (`match_signals`) because a dense DNA can bury this turn's request in a three-line reason; grouping makes that worse, not better — a family row can absorb "somewhere warm" invisibly — so the detail block's answer is promotion, not truncation, and five stated things WRAP on the client rather than truncate. The block is emitted **independently of the badge gate, on BOTH pickers**: a card whose `match` is suppressed for want of a reason still ships its receipt, and `_degraded_picker_from_rows` — which emits no badge at all — carries it through the same helper, because the per-family counts are the only honest coverage signal a traveller gets on that path and leaving the worst case the least informative is backwards. The reasons `match` is withheld (no ceiling, degraded path) say nothing about whether the family counts are honest: the evidence is a statement about the city and the traveller, the badge is a ratio. A stated codon the city does NOT hold promotes nothing and invents no row — the miss shows as that family's `n_hit < n_total`. Locked by `mywai-sherpa/tests/cognitive/test_destination_taste_evidence.py`.

**No `stay` / `budget` family appears — `DEST_NO_HOTEL_CODONS` is ON.** `"false"` in `pg_client.py:2534` is the code DEFAULT; the box10 template has set it **true** on `mywai-dna-prod-dna-shortlist` since 27 Aug (verified on the running function, 6 Sep 2026). Hotel-lane codons are stripped BEFORE the query mass is summed, so they are in neither the numerator nor the denominator — measured at **0.0 %** of query mass for `STAY.STY#BOUT` on a real profile against the deployed code. The receipt is built from the QUERY's families, so it cannot show a ring for a codon the query never carried. Rows still hold STAY codons (884 of 902) and that is the DESIGNED state: the strip is query-time only, deliberately, so the rows stay usable by whatever consumes them next. ⚠️ Read the deployed env var, not the source default, before repeating either claim.

**Staged rollout — `_BADGE_SUPPRESSION` (env `FINDER_BADGE_SUPPRESSION`, default OFF).** Phase 1 (default): the reason + telemetry land and `match` renders exactly as before, so `destination_picker_emit`'s new `reasoned` / `unreasoned` / `reason_sources` / `badge_suppression` counters measure real badge coverage first. Phase 2 (`=1`): a card with no derivable reason **omits** `match` (omitted, not nulled — both surfaces guard on `match != null`). One-way sequencing dial: once phase 2 is measured good, delete the env var and make suppression unconditional. The **degraded picker** (`_degraded_picker_from_rows`) runs the same rule on the two enrichment-free sources (stated codons, saved taste) — it now takes `stated_codons` / `taste_codons` and logs the same coverage counters.

**Four card fields from Finder v2 (additive, all optional, render-guarded with `?? fallback`):** `period` `{check_in, check_out?, nights?}` (trip dates), `est_flight` `{origin_iata, dest_iata, hours, fare_low, fare_high, currency:"EUR", estimate:true, cabin, cabin_source}` (round-trip all-pax estimate from origin), `affordability` `"within"|"stretch"` (budget verdict; `unaffordable` never reaches the card), `weather` `{avg_temp_c, rating?, condition?, months?}` (period-averaged from the climate JSONB).

**The estimate prices the cabin the SEARCH will run (ticket 17).** The cabin is resolved BEFORE the fare, by `cognitive/cabin_decision.py::resolve_cabin` — the same function `_resolve_flight` and `build_flight_search` call, so setup and the search can no longer price two different products (setup said €288–€593, the fare arrived at €1,400: an economy curve, then a taste-profile escalation to Business). `est_flight.cabin` is the canonical internal token (`economy` | `economy_plus` | `business` | `first` — `premium_economy`/`economy plus` are spellings of `economy_plus`, never emitted). `est_flight.cabin_source` is `"user"` (the traveller set it, flag and all) | `"requested"` (a cabin value with no `cabin_explicit` flag behind it) | `"taste_profile"` (we escalated it) | `"default"`. **Only `taste_profile` licenses a "picked from your taste profile" line** — nothing was chosen for an economy-leaning traveller, so nothing may be claimed for them. Three rules the code enforces: explicit-ness comes from the `cabin_explicit` FLAG and never from the truthiness of `cabin_class` (handler.py writes the cabin with no flag companion, and `_resolve_flight` gates on the flag); the band is a calibrated uplift over the finder's own economy curve, NOT `cabin_fare_estimator`'s raw multiple (which overshoots — ~€1,650 against a real €1,407); and an **unresolvable cabin emits NO `est_flight` and NO `affordability` at all**, loudly logged (`cabin_token_unrecognised` / `flight_estimate_cabin_unresolved`), because a fabricated range is never safe. The affordability verdict derives from the SAME uplifted midpoint — an economy number used to badge a business trip "within budget". Economy is unchanged: its uplift is exactly 1.0. `climate_note` remains the backward-compat fallback. `SketchFrame.destinations` stays `list[dict]` (no Pydantic change). UI: `DestinationCardData` + `DestinationCard` in `mywai-hotel-providers/ui/src/components/AgentPlayground.tsx` render the period line (`CalendarDays`), est-flight+fare line always labelled "est." (`Plane`), affordability badge (`BadgeCheck` within / `Wallet` stretch), and the upgraded weather strip (`Thermometer`, avg °C + condition + rating, falling back to `climate_note`) — lucide-react icons only.

**THE CITY'S CATALOGUE IDENTITY — `geoname_id` on the destination card (ticket 210, 2026-09-26; additive, optional).** Both card builders — `_to_card` (which builds the shown deck AND the swap `alternatives`, so a swapped-in card stays shape-identical) and `_degraded_picker_from_rows` — now emit the Aurora row's `geoname_id`. **A STRING OF ASCII DIGITS on the wire, or ABSENT.** Never `""`, never `null`, never a city name, never a placeholder.

- **Why it had to ship.** The card was assembled FROM a row that has `geoname_id` (the same value `_deck_crowds` / `_deck_wx` are keyed on, four lines below) and dropped it. Every road in the product now walks the finder, so this was the busiest destination payload in the product and the only one from which a client could not say WHICH city it held. The consumer is `mywai-prod-ti-city-enrichment` (HASH `countryCode` + RANGE `cityId`); with `country_code` already on the card, both halves of that key now come off the SAME row.
- **⚠️ STRING, NOT INT — a key-schema fact, not a style choice.** The RANGE key `cityId` is DynamoDB type **S**. Keying it `{"cityId": {"N": "3169070"}}` returns `ValidationException: The provided key element does not match the schema` (measured, first attempt). Aurora already stores the column as TEXT (`mywai-dna/tools/schema_migration.sql`: `geoname_id TEXT PRIMARY KEY`), so the normal path is a strip-and-check; `_catalogue_city_id` coerces anyway, for an int/Decimal off the RDS Data API.
- **The gate is `_catalogue_city_id` (`cognitive/sketch_engine.py`)** and it mirrors the client's `asCityId` (`mywai-demo/ui/src/lib/cityIdentity.ts`) exactly, so one identity cannot be accepted at one end of the wire and rejected at the other. ASCII digits pass; a name, `""`, a `dest-4` placeholder, a bool, a negative, a non-ASCII digit and **`"3169070.0"`** all come out ABSENT. The float matters most: truncating it would INVENT an id, and an invented id keys the catalogue for the WRONG city.
- **ABSENT IS THE POINT.** A placeholder would make "we cannot identify this city in the catalogue" indistinguishable from "this city qualifies for nothing" — the silent-partial-failure class this field exists to remove. **Name resolution is NOT an acceptable substitute anywhere:** MEASURED 26 Sep 2026, `GET /cities/MA/search?query=Marrakech` returns `[]`, because the catalogue spells it "Marrakesh".
- **Additive, MEASURED not asserted.** Both builders' cards were serialised for the same fixtures before and after the edit (the dump was first confirmed deterministic across two pre-change runs) and diffed: the only difference in the entire payload was four added `geoname_id` lines, and the no-id halves were byte-identical. `SketchFrame.destinations` stays free-form `list[dict]`, so `picker.model_dump(mode="json")` passes the key through and there is **no AppSync schema change and no forwarder-allowlist change**. NOT retrofitted: `tools/discovery_pool/contract.py` (the Path B inspiration pool) is a separate, hand-seeded shape with different field names and no GeoNames ids.
- Locked by `mywai-sherpa/tests/cognitive/test_dest_geoname_id_card.py`.

## What it does
- `decide_render` returns `{n, mode, variation_axis, variation_values, rationale}` per turn
- Decision tree: lock primitive → committed trip → DNA conviction → drop-to-commit threshold → axis confidence → cold start default
- Variation values define the spread: FORK [−0.35, +0.35], SWATCH [−0.3, 0.0, +0.3], SWIPER 7 values from −0.5 to +0.5
- LinUCB bandit (`SHERPA_BANDIT=on`) can override the mode hint once it has ≥10 reward updates
- `_choose_variation_axis` switches to a less-settled axis if the pattern default is already determined by DNA (e.g. avoiding budget/luxury fork for a known-luxury user)

## Logical flow (decision tree)
1. **Lock primitive:** any block locked by user → COMMIT immediately
2. **Committed trip:** user picked a sketch → single-sketch modification mode (COMMIT)
3. **DNA conviction > 0.7:** high confidence → COMMIT early
4. **DNA conviction > 0.45:** moderate confidence → FORK
5. **Turn ≥ drop_to_commit_turns + 1:** user has refined enough → COMMIT
6. **Axis confidence > 0.7:** strong signal on variation axis → COMMIT
7. **Axis confidence > 0.4:** decent signal → FORK
8. **Cold start:** use `mode_hint` from pattern (swatch/swiper/fork/commit)
9. **Bandit override:** if `SHERPA_BANDIT=on` and ≥10 updates → use LinUCB hint

## Critical code
```python
# render_policy.py — full decision tree (simplified)
def decide_render(pattern, taste_field, turn_number, is_cold_start,
                  bandit_mode_hint=None, dna_conviction_score=0.0,
                  has_committed_trip=False, user_locked_blocks=None):

    if user_locked_blocks and any(v for v in user_locked_blocks.values()):
        return _commit(...)                           # lock primitive
    if dna_conviction_score > 0.7 and not is_cold_start:
        return _commit(...)                           # high conviction
    if dna_conviction_score > 0.45 and not is_cold_start:
        return _fork(variation_axis, ...)             # moderate conviction
    if turn_number >= drop_turns + 1 and not is_cold_start:
        return _commit(...)                           # drop-to-commit
    # ... axis confidence checks, then cold-start mode_hint
    return _swatch(variation_axis, ...)               # default: 3-sketch swatch
```

## `mode_for_count(n)` — canonical mode from FINAL sketch count (2026-07-06)
`decide_render` picks a mode from the *intended* N before sketches are built; but the no-inventory/no-flight filters, the dedupe pass, and post-LENS over-budget/unpriced substitution can all shrink the surviving count — leaving `mode` stale (e.g. `swatch` with only 2 cards). The playground used to patch this client-side (`AgentPlayground.tsx` deriving mode from `sketches.length`). Root cause now fixed server-side:
- **`render_policy.mode_for_count(n: int) -> str`** — pure, single source of truth: `n≤1→commit`, `2→fork`, `3→swatch`, `≥4→swiper`.
- Applied at the FINAL count in two places: `sketch_engine.run_sketch_engine` (after the dedupe/no-hotel/no-flight filters, replacing the old partial 1→commit/2→fork patch) and `handler.py` post-LENS (replacing the old partial COMMIT→FORK patch).
- `RenderMode.DESTINATION_PICKER` is count-independent and set on its own path — never routed through `mode_for_count` (guarded: only applied when `sketches` is non-empty). The UI can now trust `block.mode`.

## Gotchas
- `SHERPA_BANDIT=on` must be set in env AND bandit must have ≥10 reward updates for LinUCB to override. Default (shadow mode) collects data but uses rule-based decision
- `_choose_variation_axis` silently switches the axis if the default is settled — rationale string captures why; check it in logs if users are getting unexpected variation axes
- `drop_to_commit_turns` comes from the pattern's `render_defaults` — different patterns have different turn thresholds before converging to COMMIT
